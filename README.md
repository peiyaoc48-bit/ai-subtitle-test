# AI 字幕翻译服务质量评测

[![CI](https://github.com/peiyaoc48-bit/ai-subtitle-test/actions/workflows/ci.yml/badge.svg)](https://github.com/peiyaoc48-bit/ai-subtitle-test/actions/workflows/ci.yml)

为一个基于大模型（DeepSeek）的字幕翻译服务搭建质量保障体系：接口与格式测试、LLM-as-Judge 翻译质量评测、评测数据集构建、Prompt 迭代与回归、安全测试、CI 自动化。

> 这里的实验发现，已整理成可直接使用的质检工具 [SubQA](https://github.com/peiyaoc48-bit/subqa)。

## 评测体系 2.0：MQM 错误标注 + 统计检验

1.0 版本（下文）用二元"及格 / 不及格"打分，评测集只有 45 + 7 条，95% 置信区间约 ±10 个百分点，相邻版本的差异无法区分。2.0 参照机器翻译评测的通行做法重建：

| | 1.0 | 2.0 | 依据 |
|---|---|---|---|
| 打分 | 裁判判断及格 / 不及格 | 标注每处错误的类别与严重度，按 MQM 权重扣分（critical 25 / major 5 / minor 1）| MQM；GEMBA-MQM（Kocmi & Federmann, WMT 2023）|
| 评测集 | 52 条，需手写翻译要点 | **202 条**，只需原文（从开源语料分层抽样）| MQM 无需参考译文和要点 |
| 版本对比 | 3 次运行取均值 | **bootstrap 95% 置信区间 + 配对 bootstrap 显著性检验** | Koehn (2004)，WMT 仍在使用 |
| 裁判可信度 | 未验证 | **人工盲评 50 条，计算加权 Cohen's kappa、Spearman 相关** | LLM-as-Judge 校准的常规做法 |

### 结果（202 条，`python scripts/mqm_report.py`，完整报告见 [reports/mqm_summary.md](reports/mqm_summary.md)）

| 版本 | MQM 均分（95% CI，越接近 0 越好）| 无错误 | 含 major 及以上 | 每 100 句错误 | 输入 token |
|---|---|---|---|---|---|
| v1 | -2.06（-2.63 ～ -1.56）| 59% | 24% | 68 | 34 |
| v3 | -1.54（-1.98 ～ -1.18）| 64% | 20% | 59 | 143 |
| v4 | -1.39（-1.93 ～ -0.95）| 76% | 17% | 44 | 484 |
| v5 | -1.15（-1.66 ～ -0.74）| 77% | 13% | 40 | 646 |
| v6 | -1.15（-1.64 ～ -0.71）| 76% | 12% | 40 | 808 |

| 配对检验 | 均分变化 | p 值 | 结论 |
|---|---|---|---|
| v1 → v3 | +0.52 | 0.002 | 显著更好 |
| v3 → v4 / v4 → v5 / v5 → v6 | +0.15 / +0.24 / 0.00 | 0.215 / 0.119 / 0.495 | 相邻版本差异均不显著 |
| v1 → v6 | +0.92 | 0.001 | 显著更好 |

**结论**

1. **整体迭代有效**：v1 → v6 严重错误比例从 24% 降到 12%，差异显著（p = 0.001）。
2. **相邻版本之间的提升都不显著**。1.0 里看到的逐版本提升，有相当部分落在噪声范围内；判断单次改动是否有效需要更大的评测集或更大的改动。
3. **安全加固没有损害质量**：1.0 中 v6 单句集掉到 79.3%，曾怀疑安全规则分散了模型注意力；在 202 条上 v6 与 v5 均分完全相同（p = 0.495），那次"下降"是小样本波动。
4. **改进来自哪里**：v4 的"直译 → 反思 → 意译"让风格类错误从每 100 句 24 个降到 9 个；v5 的上下文窗口让"需要上下文"组从 -1.76 提升到 -0.61。
5. **短板仍是网络梗**：各版本在网络梗组都是最差（-2.6 ～ -3.6），是下一步的改进重点。
6. **成本**：输入 token 从 34 涨到 808（约 24 倍）；全部 5 个版本 × 202 条的翻译与评审（2000 余次调用）实际花费约 0.4 元。

### 裁判可信度验证（人工盲评 + 复核，完整报告见 [reports/judge_agreement.md](reports/judge_agreement.md)）

从 v1、v6 译文中按裁判级别分层抽 50 条，人工**盲评**（看不到裁判结论）；再对 23 条分歧条目（级别不同且至少一方判为严重 / 致命）做**复核**，此时显示裁判的错误标注和理由，给出最终级别。

| 阶段 | 裁判与人工的加权 kappa | 说明 |
|---|---|---|
| 盲评 | **-0.18** | 人不受裁判影响；但标注者非英语专业，靠回译核对，漏看了性别代词错误（*我妈… → he*）等 |
| 复核后 | **0.85**（能否上线判断准确率 98%）| 23 条分歧中 21 条改为裁判的级别、0 条维持人工原判，存在明显的**锚定效应** |

**结论**

1. **裁判一致性只能给出区间 [-0.18, 0.85]，不能确认裁判可靠。** 盲评受限于标注者英语水平；复核时裁判的理由对非专业标注者说服力很强，参考答案偏向裁判，0.85 是上限而不是实测值。
2. **复核确实暴露了人工盲评的漏判**：上下文导致的代词性别错误、"不处"的网络用语含义、片名误译，盲评都没有看出来。
3. **裁判的问题也有迹可循**：对网络梗"抽象"（离谱）的直译判为无错误；部分理由自相矛盾（理由写"基本达意 / 尚可接受"却判 major）。
4. **因此**：MQM 分数用于看 v1 → v6 这种大跨度的趋势，相邻版本的小差异不作为结论（这与显著性检验的结果一致）。

**下一步**：由英语较好的第二标注者独立盲评同一批 50 条，计算人与人之间的一致性作为天花板；换用不同家族的模型（通义 / 智谱）作为第二裁判做交叉验证，同时消除裁判与被测模型同为 DeepSeek 的自我偏好。

## 评测体系 1.0（早期结果）

### Prompt 迭代（每个版本跑 3 次取均值）

| 版本 | 主要改动 | 单句评测集（45 条）| 上下文评测集（7 条）|
|---|---|---|---|
| v1 | 基础翻译指令 | 76%（1 次）| — |
| v2 | 加"口语化、简洁" | 76%（1 次），网络梗 ↑ 但语气情绪 ↓ | — |
| v3 | 去掉"简洁"，要求不漏译不添加、保留语气、意译网络梗 | **77.8%**（69% / 80% / 84%）| — |
| v4 | "直译 → 反思 → 意译"三步，JSON 输出 | **85.9%**（84% / 87% / 87%）| 23.8% |
| v5 | v4 + 上下文窗口（前 2 句、后 1 句）| 84.4%（80% / 87% / 87%），与 v4 差异在波动范围内 | **95.2%** |

| 成本（单句评测集，每条平均）| v3 | v4 | v5 |
|---|---|---|---|
| 输入 token | 143 | 484 | 646 |
| 输出 token | 16 | 105 | 104 |
| 耗时 | 0.93 s | 1.53 s | 1.24 s |

### 关键发现

1. **大模型输出失控缺陷**：62 个"呜"的字幕被翻译成原文 528 倍长的重复文本，并导致同条后半句"李娜真坏"漏译。新增译文长度比例校验用例复现后，通过 `max_tokens` 上限 + 连续重复字符预处理修复，单次耗时 46 s → 12 s。
2. **单次评测不可靠**：同一 v3 Prompt 三次运行结果为 84% / 69% / 80%，波动 15 个百分点。之后所有版本对比改为 3 次运行取均值；v4 的结构化思考将波动收窄到 3 个百分点。
3. **只看总分会掩盖问题**：v1 与 v2 总通过率相同（76%），按分类拆开后，v2 网络梗类 +15%、语气情绪类 −18%，定位到"简洁"指令导致信息压缩。
4. **逐条翻译丢失上下文**：不给上文时，"（我妈打电话来）说今晚不回来吃饭了"被译成 *He said…*。v5 引入上下文窗口后修复，上下文类 23.8% → 95.2%，单句集回归无显著退步。
5. **LLM 筛选器过度判定**：让大模型判断"是否需要上下文"，60 组判了 58 组（把"含网络梗"也算进去）；改用**差分测试**（同一句不给上文 / 给上文各译一次，只保留译文有实质差异的）后只剩 7 组，人工审核再采纳 4 组。
6. **预期结果本身也会错**：大模型生成的评测要求曾把"家里有矿"的直译 *mine at home* 写成标准答案。人工审核不仅判断用例有没有价值，也校验预期结果是否正确。

## 评测数据集构建

```
开源语料 zh-meme-sft-8k（MIT）1042 句
  → collect.py 长度筛选、去重、抽样 50 句
  → label.py 大模型分类并生成翻译要点
  → review_web.py 网页人工审核（采纳 40/50 = 80%，人工修改 3 条）
  → merge.py 并入评测集：45 条，7 个分类

对话语料 → context_candidates.py 大模型初筛（58/60）
  → context_filter.py 差分测试（7/58）→ 人工审核（4/7）
  → 加 3 条手写用例：上下文评测集 7 条
```

## 项目结构

```
app/                    被测服务（FastAPI 字幕翻译接口）
  main.py               接口：POST /translate、GET /health
  srt.py                SRT 解析与序列化
  translator.py         翻译器：mock / 真实大模型；JSON 输出解析、上下文窗口、成本统计
prompts/                Prompt v1 – v5
data/
  samples/              测试字幕（含超长重复、HTML 标签、多行等边界数据）
  eval/                 评测集：cases.json（单句）、context_cases.json（上下文）
  corpus/               语料抽取、标注、审核的中间结果
tests/
  test_api.py           接口测试：正常流程、参数校验、异常输入
  test_srt_format.py    格式测试：条数、序号、时间轴、换行、译文长度比例
  test_preprocess.py    预处理单元测试
  quality/              翻译质量评测（DeepEval，裁判模型为 DeepSeek）
scripts/                语料流水线、审核工具、评测报告
reports/                每次评测的 JUnit 结果、译文明细与成本统计
.github/workflows/      GitHub Actions：提交即回归，结果推送到微信
```

## 快速开始

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pytest                                  # mock 模式，不调用大模型
uvicorn app.main:app --reload           # 启动服务，打开 http://127.0.0.1:8000/docs
```

### 接入真实大模型与质量评测

```bash
./scripts/download_corpus.sh            # 下载开源语料
python scripts/build_mqm_set.py         # 构建 202 条评测集
python scripts/run_mqm.py v1 v5 v6      # MQM 评测（断点续跑、并发、余额保护）
python scripts/mqm_report.py v1 v5 v6   # 置信区间、显著性检验、错误分布
```

```bash
cp .env.example .env                    # 填入 DeepSeek API Key（.env 不会被提交）
set -a; source .env; set +a
pip install deepeval
PROMPT_VERSION=v5 pytest tests/quality --junitxml=reports/eval_v5.xml
python scripts/eval_report.py v4 v5     # 按分类对比各版本
```
