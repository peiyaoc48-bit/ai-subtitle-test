# AI 字幕翻译服务质量评测

[![CI](https://github.com/peiyaoc48-bit/ai-subtitle-test/actions/workflows/ci.yml/badge.svg)](https://github.com/peiyaoc48-bit/ai-subtitle-test/actions/workflows/ci.yml)

为一个基于大模型（DeepSeek）的字幕翻译服务搭建质量保障体系：接口与格式测试、LLM-as-Judge 翻译质量评测、评测数据集构建、Prompt 迭代与回归、安全测试、术语一致性（RAG 与 Agent）评测、CI 自动化。

> 这里的实验发现，已整理成可直接使用的质检工具 [SubQA](https://github.com/peiyaoc48-bit/subqa)。

## 评测体系 2.0：MQM 错误标注 + 统计检验

1.0 版本（下文）用二元"及格 / 不及格"打分，评测集只有 45 + 7 条，95% 置信区间约 ±10 个百分点，相邻版本的差异无法区分。2.0 参照机器翻译评测的通行做法重建：

| | 1.0 | 2.0 | 依据 |
|---|---|---|---|
| 打分 | 裁判判断及格 / 不及格 | 标注每处错误的类别与严重度，按 MQM 权重扣分（critical 25 / major 5 / minor 1）| MQM；GEMBA-MQM（Kocmi & Federmann, WMT 2023）|
| 评测集 | 52 条，需手写翻译要点 | **1002 条**，只需原文（从开源语料抽样）| MQM 无需参考译文和要点 |
| 版本对比 | 3 次运行取均值 | **bootstrap 95% 置信区间 + 配对 bootstrap 显著性检验** | Koehn (2004)，WMT 仍在使用 |
| 裁判可信度 | 未验证 | **人工盲评 50 条，计算加权 Cohen's kappa、Spearman 相关** | LLM-as-Judge 校准的常规做法 |

### 结果（1002 条，`python scripts/mqm_report.py`，完整报告见 [reports/mqm_summary.md](reports/mqm_summary.md)）

评测集最初是 202 条，相邻版本之间分不出差异；之后保留原有条目、从语料再抽 800 条扩到 1002 条（`build_mqm_set.py extend 800`），已有结果直接复用。

| 版本 | MQM 均分（95% CI，越接近 0 越好）| 无错误 | 含 major 及以上 | 每 100 句错误 | 输入 token |
|---|---|---|---|---|---|
| v1 | -2.33（-2.66 ～ -2.04）| 60% | 24% | 72 | 35 |
| v3 | -1.68（-1.92 ～ -1.48）| 67% | 20% | 57 | 144 |
| v4 | -1.44（-1.67 ～ -1.25）| 74% | 18% | 46 | 485 |
| v5 | -1.25（-1.47 ～ -1.06）| 76% | 16% | 42 | 646 |
| v6 | -1.24（-1.48 ～ -1.02）| 77% | 14% | 40 | 808 |

| 配对检验 | 202 条：变化 / p | 1002 条：变化 / p |
|---|---|---|
| v1 → v3 | +0.52 / 0.002 | +0.65 / < 0.001 |
| v3 → v4 | +0.15 / 0.215 | +0.24 / **0.014** |
| v4 → v5 | +0.24 / 0.119 | +0.19 / **0.035** |
| v5 → v6 | 0.00 / 0.495 | +0.01 / 0.427 |
| v1 → v6 | +0.92 / 0.001 | +1.09 / < 0.001 |

**结论**

1. **整体迭代有效**：v1 → v6 含 major 及以上错误的句子从 24% 降到 14%（p < 0.001）。
2. **样本扩大 5 倍后，v3 → v4、v4 → v5 也变得显著**；202 条时这两步落在噪声范围内。但这两步只在 DeepSeek 裁判下显著，换裁判后不成立（见下文交叉验证）；共做了 7 组比较、未做多重比较校正，p = 0.035 只算勉强显著。
3. **安全加固没有损害质量**：v5 → v6 在两个样本量下都没有差异（p = 0.43 ～ 0.50）。1.0 中 v6 单句集掉到 79.3%，那次"下降"是小样本波动。
4. **改进来自哪里**：v4 的"直译 → 反思 → 意译"让风格类错误从每 100 句 29 个降到 12 个；v5 的上下文窗口在原 202 条（含真实上文的用例）中让"需要上下文"组从 -1.76 提升到 -0.61（新增的 800 条没有上文，这一组的提升被稀释）。
5. **短板仍是网络梗**：各版本在网络梗组都是最差（-3.0 ～ -5.1），是下一步的改进重点。
6. **成本**：输入 token 从 35 涨到 808（约 23 倍）；5 个版本 × 1002 条的翻译与评审（约 1 万次调用）DeepSeek 实际花费约 4 元。

### 裁判可信度验证（人工盲评 + 复核，完整报告见 [reports/judge_agreement.md](reports/judge_agreement.md)）

从 v1、v6 译文中按裁判级别分层抽 50 条，人工**盲评**（看不到裁判结论）；再对 23 条分歧条目（级别不同且至少一方判为严重 / 致命）做**复核**，此时显示裁判的错误标注和理由，给出最终级别。

| 阶段 | 裁判与人工的加权 kappa | 说明 |
|---|---|---|
| 盲评 | **-0.18** | 人不受裁判影响；但标注者非英语专业，靠回译核对，漏看了性别代词错误（*我妈… → he*）等 |
| 复核后 | **0.85**（能否上线判断准确率 98%）| 23 条分歧中 21 条改为裁判的级别、0 条维持人工原判，存在明显的**锚定效应** |

**结论**

1. **裁判一致性只能给出区间 [-0.18, 0.85]，不能确认裁判可靠。** 盲评受限于标注者英语水平；复核时裁判的理由对非专业标注者说服力很强，参考答案偏向裁判，0.85 是上限而不是实测值。
2. **复核确实暴露了人工盲评的漏判**：上下文导致的代词性别错误、"不处"的网络用语含义、片名误译，盲评都没有看出来。
3. **裁判的问题也有迹可循**：对网络梗"抽象"（离谱）的直译判为无错误；部分理由自相矛盾（理由写"基本达意 / 尚可接受"却判 major）。
4. **因此**：MQM 分数用于看 v1 → v6 这种大跨度的趋势，相邻版本的小差异要经过跨模型验证才作为结论。

### 跨模型裁判交叉验证（DeepSeek vs 通义 qwen-plus，完整报告见 [reports/cross_judge.md](reports/cross_judge.md)）

同一批译文（5 个版本 × 1002 条，均由 DeepSeek 翻译）只换裁判，用同一套 MQM 标准重评（`python scripts/cross_judge.py run` / `report`）。

| 版本 | DeepSeek 裁判 | qwen-plus 裁判 | 含 major 及以上（DS / Qwen）|
|---|---|---|---|
| v1 | -2.33 | -4.57 | 24% / 55% |
| v3 | -1.68 | -4.10 | 20% / 51% |
| v4 | -1.44 | -4.21 | 18% / 50% |
| v5 | -1.25 | -4.07 | 16% / 50% |
| v6 | -1.24 | -3.86 | 14% / 48% |

| 检验（1002 条）| DeepSeek 裁判 | qwen-plus 裁判 | 两个裁判是否一致 |
|---|---|---|---|
| v1 → v3 | +0.65，p < 0.001 | +0.47，p = 0.001 | 一致：显著更好 |
| v3 → v4 | +0.24，p = 0.014 | -0.11，p = 0.756 | 不一致 |
| v4 → v5 | +0.19，p = 0.035 | +0.14，p = 0.179 | 不一致 |
| v5 → v6 | +0.01，p = 0.427 | +0.21，p = 0.064 | 一致：不显著 |
| v1 → v6 | +1.09，p < 0.001 | +0.71，p < 0.001 | 一致：显著更好 |

版本排名的 Spearman 相关从 202 条时的 0.70 升到 0.90；逐句最严重级别的加权 kappa 为 0.40（202 条时 0.41），能否上线判断一致 65%。

**结论**

1. **两个裁判都认可的结论：v1 → v3、v1 → v6 显著变好；v5 → v6 没有变差。** v3 → v4、v4 → v5 的提升只有 DeepSeek 认可，不作为结论。样本从 202 扩到 1002 条，v1 → v3 从"依赖裁判"变成了"两个裁判一致"。
2. **MQM 绝对分数依赖裁判，不能跨裁判比较**：qwen-plus 把约一半句子判为含 major 错误，DeepSeek 只有 14% ～ 24%；39% 的句子 qwen 更严，DeepSeek 更严的只有 3%。
3. **更严不等于更准**：抽查 qwen 判 major、DeepSeek 判无错误的句子（202 条时 93 条），qwen 有真发现（"白 → pale"的负面含义），也有明显误判（把"byt"（避孕套拼音缩写）当成毒品、认为"抽象 → random"不等价、"big lightweight"属语义矛盾）。
4. **自我偏好无法单独确认**：DeepSeek 对 DeepSeek 译文更宽松，与自我偏好的预期一致，但也可能只是两个模型的严格程度不同；需要不同家族模型的译文才能区分。
5. **两个裁判之间的一致性（0.40）高于任一裁判与人工盲评的一致性（-0.18 / -0.02）**；与复核答案的一致性 DeepSeek 0.85、qwen 0.58，但复核时看的是 DeepSeek 的理由，这一差距部分来自锚定效应。

**评测方法上的启示**：LLM 裁判适合在**同一裁判**下做相对比较（版本 A 是否比 B 好），不适合给出绝对质量分；结论要在至少两个不同家族的裁判下都成立才可信。

**下一步**：由英语较好的第二标注者独立盲评同一批 50 条，计算人与人之间的一致性作为天花板；用不同家族模型翻译同一批句子，区分自我偏好与裁判严格程度。

## 术语一致性：RAG 与 Agent（完整报告见 [reports/rag_summary.md](reports/rag_summary.md)）

**问题来源**：SubQA 的人名一致性检查发现，同一个角色在不同字幕里会被译成不同的英文名。字幕本地化团队的做法是为每部剧维护一份**剧集设定表**（show bible），规定人名、称谓、地名怎么译。这里让模型在翻译时自动查这张表，并评测"程序先检索再翻译"（RAG）和"模型自己决定查什么"（Agent）两种方式。

**评测数据**（`data/glossary/`）：
- 设定表：为避免版权问题，用一部虚构的古装剧《长安夜行》，30 个条目，覆盖人名、称谓、地名、组织、物品、节日；其中 6 个条目带同形词说明（"一世长安"的长安意为平安）。
- 台词：按 8 类难点生成后用规则校验，再人工复核，复核记录在 `review.json`。最终 238 条：全名、别名、称谓、多术语、带上文、同形词、无术语、未登记叫法。
- 人工复核发现，**生成数据的模型自己就分不清同形词**：它把"白玉簪子""天机不可泄露"里的词也标成了专有名词；人工复核纠正了 12 条标注、删除 1 条有歧义的用例，"未登记叫法"另删掉 20 条指代模糊或重复的。

### 检索质量（测试集 119 条；向量检索的相似度门槛在另一半开发集上选）

| 检索器 | 精确率 | 召回率 | F1 | 未登记叫法召回 | 同形词误检 |
|---|---|---|---|---|---|
| 关键词（最长匹配） | 90% | 86% | 0.88 | 20% | 100% |
| 向量 top3（text-embedding-v4） | 64% | 76% | 0.69 | 80% | 64% |
| 混合：关键词 + 向量 top1 | 86% | 93% | **0.90** | 63% | 100% |

- 设定表里登记过的写法，关键词检索全部能找到；向量检索的价值只在**没登记的叫法**上（"林家那丫头""萧家那位储君"）。
- 向量相似度能区分"这句和剧情有没有关系"（无术语句子相似度中位数 0.30，有术语的 0.54），但**分不清具体是哪个条目**（正确条目和最像的错误条目分数严重重叠）。
- **同形词所有检索器都会误检**，只能交给翻译模型根据设定表里的注意事项判断。

### 端到端（191 条，"未登记叫法"不计入：这类句子忠实的译文本来就不该出现人名）

术语准确率 = 该用设定译名的地方用对了没有，按字符串匹配，不依赖裁判模型。

| 方式 | 术语准确率（95% CI）| 同形词误用 | 每句输入 token | 每句耗时 |
|---|---|---|---|---|
| 不给设定表（v6） | 60.9%（55.0% ～ 67.2%）| 3% | 811 | 1.1s |
| **关键词检索 + v7** | **89.0%**（85.0% ～ 93.0%）| 3% | 1013 | 1.0s |
| 直接给正确条目 + v7（上限） | 90.1%（86.2% ～ 94.1%）| 3% | 1006 | 1.1s |
| Agent，修复前 | 82.9%（77.8% ～ 87.6%）| 0% | 4446 | 3.5s |
| Agent，修复后 | 86.2%（81.8% ～ 90.1%）| 0% | 2862 | 2.5s |

**结论**

1. **加设定表后术语准确率从 61% 升到 89%**（p < 0.001），而且关键词检索已经接近"直接给正确条目"的上限（90%）。**检索不是瓶颈**，所以没有在端到端里再加向量检索。
2. **剩下的错误不在检索，也不在模型，而在设定表**：人工复核了"上限"条件下剩余的 25 处，**没有误译**，其中 21 处是昵称、当面称呼（婉儿 → *Wan'er*，七哥 → *Brother Qi*），设定表本身没有规定怎么译；4 处没用统一译名但意思正确（密卷 → *the scroll*）。下一步是给设定表补上称呼的译法，而不是继续调检索。
3. **Agent 不划算**：准确率比 RAG 低 3 个百分点，输入 token 是 RAG 的 2.8 倍，耗时是 2.5 倍；唯一的优势是同形词误用为 0。
4. **评测发现了 Agent 的死循环缺陷**：第一版格式检查工具只报"第 1 行 43 个字符，超过 42"，模型数不清字符，反复改错行，**37% 的句子耗尽步数也没有提交**。修复方法：工具直接返回程序算好的断行建议、工具结果附带剩余步数、提示词限定检查次数。修复后 **100% 正常提交**，平均步数从 4.9 降到 3.2，相关回归测试见 `tests/test_agent.py`。
5. **打分规则也被评测发现了问题**：第一版只认 *Xiao Jingheng*，但设定表的说明写着"二皇子"译 *the Second Prince*。修正为同时接受说明里规定的称呼译法（`accept` 字段），用已保存的译文重新打分（`rag_eval.py rescore`），没有重新生成译文。

**Agent 的测试**：用按剧本回复的假模型驱动 Agent，不花钱、结果确定，覆盖参数不是 JSON、调用不存在的工具、缺参数、直接回复文字不提交、超过步数上限、字幕里伪造标签等异常情况（`tests/test_agent.py`，20 个用例）。

## 评测体系 1.0（早期结果）

### Prompt 迭代（每个版本跑 3 次取均值）

| 版本 | 主要改动 | 单句评测集（45 条）| 上下文评测集（7 条）|
|---|---|---|---|
| v1 | 基础翻译指令 | 76%（1 次）| — |
| v2 | 加"口语化、简洁" | 76%（1 次），网络梗 ↑ 但语气情绪 ↓ | — |
| v3 | 去掉"简洁"，要求不漏译不添加、保留语气、意译网络梗 | **77.8%**（69% / 80% / 84%）| — |
| v4 | "直译 → 反思 → 意译"三步，JSON 输出 | **85.9%**（84% / 87% / 87%）| 23.8% |
| v5 | v4 + 上下文窗口（前 2 句、后 1 句）| 84.4%（80% / 87% / 87%），与 v4 差异在波动范围内 | **95.2%** |

| 成本（单句评测集，每条平均）| v3 | v4 | v5 |
|---|---|---|---|
| 输入 token | 143 | 484 | 646 |
| 输出 token | 16 | 105 | 104 |
| 耗时 | 0.93 s | 1.53 s | 1.24 s |

### 关键发现

1. **大模型输出失控缺陷**：62 个"呜"的字幕被翻译成原文 528 倍长的重复文本，并导致同条后半句"李娜真坏"漏译。新增译文长度比例校验用例复现后，通过 `max_tokens` 上限 + 连续重复字符预处理修复，单次耗时 46 s → 12 s。
2. **单次评测不可靠**：同一 v3 Prompt 三次运行结果为 84% / 69% / 80%，波动 15 个百分点。之后所有版本对比改为 3 次运行取均值；v4 的结构化思考将波动收窄到 3 个百分点。
3. **只看总分会掩盖问题**：v1 与 v2 总通过率相同（76%），按分类拆开后，v2 网络梗类 +15%、语气情绪类 −18%，定位到"简洁"指令导致信息压缩。
4. **逐条翻译丢失上下文**：不给上文时，"（我妈打电话来）说今晚不回来吃饭了"被译成 *He said…*。v5 引入上下文窗口后修复，上下文类 23.8% → 95.2%，单句集回归无显著退步。
5. **LLM 筛选器过度判定**：让大模型判断"是否需要上下文"，60 组判了 58 组（把"含网络梗"也算进去）；改用**差分测试**（同一句不给上文 / 给上文各译一次，只保留译文有实质差异的）后只剩 7 组，人工审核再采纳 4 组。
6. **预期结果本身也会错**：大模型生成的评测要求曾把"家里有矿"的直译 *mine at home* 写成标准答案。人工审核不仅判断用例有没有价值，也校验预期结果是否正确。

## 评测数据集构建

```
开源语料 zh-meme-sft-8k（MIT）1042 句
  → collect.py 长度筛选、去重、抽样 50 句
  → label.py 大模型分类并生成翻译要点
  → review_web.py 网页人工审核（采纳 40/50 = 80%，人工修改 3 条）
  → merge.py 并入评测集：45 条，7 个分类

对话语料 → context_candidates.py 大模型初筛（58/60）
  → context_filter.py 差分测试（7/58）→ 人工审核（4/7）
  → 加 3 条手写用例：上下文评测集 7 条
```
